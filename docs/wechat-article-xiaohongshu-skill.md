# 我用 OpenClaw 写了一个小红书自动获客 Skill，踩完这些坑后全部告诉你

> 专注于AI技术前沿分享，用最接地气的话讲最前沿的科技是我的专长，让每个人都能玩转AI是我的初心。

---

## 起因：运营人员的获客之痛

做医美行业的朋友应该都有感触——每天运营同事在小红书、抖音、微博、微信生态、好大夫等各种平台上翻帖子、看评论、找潜在客户。一个人一天能翻多少？50篇帖子？100条评论？还得肉眼判断这个人是不是真的想做热玛吉、是不是在我们的服务区域。

这件事效率太低了。

我之前写过一篇文章叫《未来最值钱的不是 OpenClaw，而是会养 OpenClaw 的人》，里面提到一个观点：**未来的商业机会，就是定制 Skills**。不是卖工具本身，而是卖「会用工具的能力」——帮客户把一套自动化流程封装成一个 Skill，让 AI 一键调用。

所以我给自己立了个课题：通过 OpenClaw 调用自动化技能，协同无头浏览器，在各大公开内容平台上，围绕预设关键词进行内容检索、评论提取和用户线索整理，形成标准化线索池，辅助团队开展合规触达与转化跟进。

**小红书，是我选的第一个试验场。** 原因很简单——它的评论区用户意向最密集，一条「这个热玛吉多少钱啊」的评论，背后大概率就是一个潜在客户。

但理想很丰满，现实嘛……全是坑。

---

## 坑一：不是所有路都能走通

一开始我没打算自己造轮子。

**第一个尝试：Python + CDP。** 用 Python 的 playwright 库直连 Chrome DevTools Protocol，思路很常规。但小红书的 SPA 架构加上各种异步加载，Python 跑起来总是漏数据，而且远程服务器上的 OpenClaw 根本看不到小红书的登录界面——你连登都登不上。

**第二个尝试：现成的 web-access Skill。** 这是一个通用的网页访问技能，但面对小红书这种重度 SPA + 反爬的站点，它就像拿一把瑞士军刀去拆炸弹——太通用了，处理不了细节。

**第三个尝试：已有的 xiaohongshu Skill。** 社区里有人做过小红书相关的技能，但效果也不理想——要么登录流程跑不通，要么评论抓不全，要么直接被反爬封掉。

三种方案都试了，都不好使。

**那就只能自己造了。**

我的方案核心是解决三个根本问题：

**登录问题**：小红书不登录搜索页是空的。我的做法是提取页面上的 QR 码 base64 图片数据，保存为 PNG 文件，用系统默认图片查看器打开（macOS 用 `open`、Windows 用 `start`、Linux 用 `xdg-open`），用户手机扫码后，脚本每 3 秒轮询登录状态，成功后自动保存 Cookie。

**Cookie 复用**：登录一次，后续运行直接加载已保存的 Cookie，跳过登录。加载前还会过滤掉过期的 Cookie（检查 Unix 时间戳），避免因为过期 Cookie 导致诡异的登录失效问题。

```javascript
// Cookie 过期过滤 —— 一行代码省了无数排查时间
const validCookies = cookies.filter(c =>
  !c.expires || c.expires === -1 || c.expires > Date.now() / 1000
);
```

这个看起来简单，但你不做这一步，线上跑着跑着就会莫名其妙掉登录，而且根本不报错——因为 Cookie 还在，只是过期了。

## 坑二：评论永远加载不完

搞定登录只是开始。真正的挑战是**拿到完整的评论数据**。

小红书是标准的 SPA（Single Page Application），评论区采用懒加载——你不滚动到底部，新评论就不会加载。如果你用常规爬虫思维「请求一个 API 拿全量数据」，抱歉，没这个 API。

**所以必须模拟一个真人在那里刷评论的过程。**

我设计了一个**三速滚动状态机**：

```
滚动速度：
  slow   → 0.5 × 视口高度（模拟仔细阅读）
  normal → 0.7 × 视口高度（正常浏览）
  fast   → 0.9 × 视口高度（快速扫过）
```

但光有速度变化还不够，真人不会匀速滚动。所以每次滚动不是一次性滑到位，而是分**1-3次微推**完成，每次推送之间有 300-700ms 的随机延迟，加上 ±50px 的抖动。

```javascript
// 单次滚动分解为多次微推
let pushCount = largeMode ? 3 + randomInt(0, 2) : randomInt(1, 3);
for (let i = 0; i < pushCount; i++) {
  const jitter = randomInt(-50, 50);
  await page.evaluate((dist) => {
    window.scrollBy({ top: dist, behavior: "smooth" });
  }, scrollDist / pushCount + jitter);
  await sleep(randomInt(DELAYS.HUMAN_DELAY.min, DELAYS.HUMAN_DELAY.max));
}
```

**最精彩的部分是停滞检测。** 有时候你滚了半天，`scrollHeight` 没变——可能是网络慢，也可能是触发了反爬限制。我的状态机会这样处理：

1. **正常状态**：每次滚动后对比 scrollHeight，如果变了说明有新内容加载
2. **停滞状态**：连续 5 次滚动 scrollHeight 没变 → 进入「大步模式」，每次 3-5 个微推
3. **死亡螺旋**：连续 20+ 次还没变化 → 执行最后的「冲刺」，直接滚到最底部
4. **退出条件**：检测到「THE END」标记，或评论数达到 500 上限

另外还有一个容易被忽略的细节——很多评论是折叠的。小红书的「展开 N 条回复」按钮必须点击才能展开子评论。我的脚本在滚动过程中会**周期性地检查并点击这些展开按钮**，确保不遗漏嵌套评论。

## 坑三：被反爬检测了

滚动的问题解决了，但如果浏览器被识别为自动化工具，一切白搭。

小红书的反爬检测点很多，最典型的就是 `navigator.webdriver` 属性。正常浏览器这个值是 `undefined`，但 Playwright 启动的浏览器默认是 `true`——等于直接告诉网站「我是机器人」。

**我的反爬是多层的，不是单点突破而是全面伪装。**

**第一层：rebrowser-patches。** 这是一个专门修补 CDP（Chrome DevTools Protocol）泄露的开源库。Playwright 通过 CDP 控制浏览器，这个协议本身会留下痕迹——比如 `window.cdc_` 开头的变量、`Runtime.enable` 调用记录等。rebrowser-patches 把这些痕迹全部抹掉。

**第二层：浏览器指纹伪装。** 光抹掉 CDP 痕迹不够，网站还会通过浏览器指纹来识别你：

```javascript
// UA 轮换 —— 每次启动随机选一个
const USER_AGENTS = [
  "Mozilla/5.0 ... Chrome/131.0.0.0 Safari/537.36",
  "Mozilla/5.0 ... Chrome/130.0.0.0 Safari/537.36",
  // ... 5 个不同版本
];

// 视口抖动 —— 不是精确的 1280x800，而是 1260~1300 × 780~820
const viewport = {
  width: 1280 + randomInt(-20, 20),
  height: 800 + randomInt(-20, 20)
};

// 伪造插件列表、硬件信息、语言设置
Object.defineProperty(navigator, 'hardwareConcurrency', { get: () => 8 });
Object.defineProperty(navigator, 'deviceMemory', { get: () => 8 });
```

**第三层：自动化标记清理。** 即使用了 rebrowser-patches，还是要再扫一遍：

```javascript
// 删除所有 cdc_ 开头的自动化标记
for (const key of Object.keys(window)) {
  if (key.match(/^cdc_/)) delete window[key];
}
// 伪造 chrome.runtime（正常 Chrome 有，自动化的没有）
window.chrome = { runtime: { connect: () => {}, sendMessage: () => {} } };
```

**哲学就是：打不到就假装。** 不是去破解人家的检测算法，而是让你的浏览器「看起来」和真人的一模一样。

## 灵光一闪：两阶段过滤架构

评论拿到了，但原始数据里全是噪音——表情包回复、作者自问自答、广告评论、@好友的互动……如果全部扔给 Claude 分析，一是 token 成本高，二是噪音会干扰判断。

**我的解决方案是「粗筛 + 精选」，脚本和 AI 各管一半。**

**第一阶段：脚本去噪（filter-comments.js）**

规则简单粗暴但有效：
- 作者自己的回复 → 删（这是运营话术，不是用户意向）
- 纯表情/纯 @ → 删（没有语义信息）
- 包含广告关键词（「免费领取」「加我微信」「招聘」） → 删
- 中文字符不足 2 个 → 删

这一步能过滤掉 40-60% 的噪音，关键是**零成本**——不调 API、不花 token。

**第二阶段：AI 语义分析**

剩下的评论交给 Claude，做三件事：
1. **意向标签**：`["购买意向", "咨询", "深度讨论", "分享经验"]`
2. **意向评分**：1-10 分（≥6 分算合格线索）
3. **判断理由**：一句话说明为什么给这个分

比如这条评论「姐妹们深圳有没有靠谱的热玛吉机构推荐啊 想做好久了」，AI 会标记为：购买意向 + 咨询，评分 8，理由「明确表达做热玛吉的意愿，且在寻找机构」。

**这个架构的妙处在于分工清晰**：脚本负责「确定不要的」（100% 精确删除），AI 负责「可能想要的」（语义理解 + 判断）。脚本是粗滤网，AI 是精细筛。

## 别人不知道的秘密武器：site-patterns

做爬虫的人都知道，网站会改版。昨天能用的选择器，今天可能就失效了。

**传统做法**是：出了 bug → 排查 → 发现选择器变了 → 修复 → 祈祷不要再变。

**我的做法**是建了一个站点经验文档（`site-patterns/xiaohongshu.md`），专门记录和小红书打交道时踩过的每一个坑：

| 发现 | 影响 | 解法 |
|------|------|------|
| SPA 架构，评论懒加载 | 不滚动就没数据 | 手动滚动 + 等待循环 |
| 不登录搜索页为空 | Cookie 是刚需 | QR 码登录流程 |
| `__INITIAL_STATE__` vs DOM 不一致 | 滚出来的评论不在 state 里 | 以 state 为主，DOM 为辅 |
| 弹窗模态 vs 全页面两种视图 | 选择器不同 | 多选择器降级策略 |
| Cookie 过期时间是 Unix 秒 | 过期 Cookie 静默失败 | 加载前过滤 |
| 「展开N条回复」点太多次会阻塞 | 页面卡死 | 设置点击上限 |

目前一共沉淀了 **27 条经验**。

这个文档的价值不只是给我自己查。当 Claude 下次执行这个 Skill 遇到问题时，它可以参考这些经验**直接规避已知的坑**，而不是每次都从零开始试错。这就像给 AI 装了一个「记忆模块」——不是靠大模型的训练数据来理解小红书，而是靠实战积累的一手经验。

## 效果展示：从评论到线索池

最终的输出是一张 **16 列的 Excel 表格**，按功能分成 4 个区域：

| 区域 | 包含列 | 作用 |
|------|--------|------|
| 用户信息 | 用户名、主页链接、IP属地 | 知道这个人是谁、在哪里 |
| 兴趣分析 | 评论原文、意向标签、意向评分、判断理由 | AI 分析的核心输出 |
| 帖子信息 | 帖子标题、链接、截图 | 溯源上下文 |
| 跟进管理 | 跟进状态、备注 | 留给运营团队填写 |

评分 ≥8 的行自动标绿，≥6 的标黄。同一个用户在不同帖子下的多条评论会被合并成一行，用 ①②③ 编号区分。运营团队拿到这张表，可以直接按评分排序开始跟进。

## 最后的思考

小红书只是开始。

这个 Skill 的架构——「搜索 → 采集 → 过滤 → 分析 → 输出」——是可以迁移到其他平台的。抖音的评论区、微博的超话、微信生态的文章留言、好大夫的患者提问……底层逻辑都是一样的：**围绕关键词找到讨论的人，判断谁是潜在客户**。

不同平台只是换了一套反爬策略和 DOM 选择器而已。这也是为什么我要做 site-patterns 经验记录——每个平台攻克一次，经验就沉淀下来，AI 下次执行就能复用。

**未来最值钱的不是 OpenClaw，而是会养 OpenClaw 的人。**

这句话不是口号。当你能把一个获客流程封装成 Skill，再配上持续化的维护服务（选择器更新、反爬升级、新平台适配），这就是一门可持续的生意。

Skill 不是一次性的代码，它是一套**可进化的自动化能力**。
